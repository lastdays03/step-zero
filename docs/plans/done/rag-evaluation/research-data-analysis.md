## 1. 데이터 구조 개요

ActionKit 데이터는 **2개 도메인**으로 구분됩니다:

| 도메인 | 설명 | 카테고리 수 | 아이템 수 |
|--------|------|------------|-----------|
| `laws` (LAW_DATA) | 법령 원문 참조 | 6개 | 21개 |
| `kits` (ACTION_KIT_DATA) | 실무 액션 키트 | 4개 (+ all) | 25개 |
| **합계** | | **10개** | **46개** |

### 1.1 LAW_DATA 상세 (laws 도메인)

| 카테고리 (slug) | 제목 | 아이템 수 | 하이라이트 보유 | 하이라이트 총 수 |
|----------------|------|-----------|---------------|----------------|
| 1 | Ⅰ. 입지 적법성 | 5 | 3/5 | 9 |
| 2 | Ⅱ. 영업 성립 요건 | 3 | 2/3 | 6 |
| 3 | Ⅲ. 안전소방 요건 | 3 | 1/3 | 3 |
| 4 | Ⅳ. 영업 중 준수의무 | 3 | 1/3 | 3 |
| 5 | Ⅴ. 위반 시 대응 절차 | 1 | 1/1 | 3 |
| 6 | Ⅵ. 행정처분 및 구제 | 6 | 6/6 | 18 |
| **합계** | | **21** | **14/21 (67%)** | **42** |

**주요 필드 구성:**
- `name`: 법령명 + 조항 (예: "건축법 제2조 (용도 분류)")
- `summary`: 1~2문장 요약 (평균 40~60자)
- `highlights`: 핵심 체크포인트 3개씩 (있는 경우)
- `ext`: 파일 확장자 (모두 `.pdf`)
- `size`: 파일 크기 표시 (예: "327KB")
- `path`: PDF 원본 파일 경로

### 1.2 ACTION_KIT_DATA 상세 (kits 도메인)

| 카테고리 (slug) | 제목 | 아이템 수 | relatedLaws 총 수 | dday 보유 |
|----------------|------|-----------|-------------------|-----------|
| legal | 법률 키트 | 11 | 19 | 0 |
| tax | 세무 키트 | 3 | 5 | 0 |
| hr | 인사 키트 | 8 | 11 | 0 |
| grant | 공고문 키트 | 3 | 3 | 2 (D-20, D-10) + 1 (상시) |
| **합계** | | **25** | **38** | **3** |

**주요 필드 구성:**
- `tag`: 분류 태그 (예: "[용도 확인]", "[근로계약]") - 모든 kit 아이템 보유
- `name`: 키트 이름 (예: "건축법 제2조 (용도 분류) 기반 검토 키트")
- `summary`: 실무 설명 1문장 (평균 20~30자)
- `type`: 파일 유형 (PDF 18개, HWP 5개, PPTX 1개, PDF 1개)
- `path`: 원본 파일 경로
- `relatedLaws[]`: 관련 법조항 이름 + 요약 (평균 1~3개)
- `dday`: 신청 마감일 (grant 카테고리에만 존재)

## 2. DB 모델 분석 (5개 테이블)

### 2.1 테이블 구조 및 관계

```
ActionKitCategory (1)  ──<  ActionKitItem (N)
                                │
                    ┌───────────┼───────────┐
                    │           │           │
              Highlight (N)  RelatedLaw (N)  File (N)
```

### 2.2 각 필드의 Q&A 활용 가능성 평가

#### ActionKitCategory
| 필드 | Q&A 활용도 | 활용 방법 |
|------|-----------|----------|
| `domain` | ★★★ | 질문 라우팅 분류 (laws vs kits) |
| `slug` | ★★ | 카테고리 식별자, 필터링 |
| `title` | ★★★ | 카테고리 수준 질문 생성 ("입지 적법성이란?") |

#### ActionKitItem
| 필드 | Q&A 활용도 | 활용 방법 |
|------|-----------|----------|
| `name` | ★★★★ | 질문의 주제 (법령명/키트명) |
| `summary` | ★★★★★ | 답변의 핵심 내용 (가장 중요) |
| `tag` | ★★★ | 질문 분류/태깅, 관련 질문 그룹화 |
| `ext`/`file_type` | ★ | 부수적 정보 |
| `dday` | ★★ | 시한 관련 질문 ("마감일이 언제?") |

#### ActionKitItemHighlight
| 필드 | Q&A 활용도 | 활용 방법 |
|------|-----------|----------|
| `content` | ★★★★★ | 체크리스트/주의사항 질문의 답변 |

#### ActionKitRelatedLaw
| 필드 | Q&A 활용도 | 활용 방법 |
|------|-----------|----------|
| `law_name` | ★★★★ | 법적 근거 인용, "어떤 법에 해당?" 유형 질문 |
| `law_summary` | ★★★★ | 법 조항 설명 질문의 답변 |

#### ActionKitFile
| 필드 | Q&A 활용도 | 활용 방법 |
|------|-----------|----------|
| `object_key` | ★ | 파일 위치 참조 (간접 활용) |
| `original_filename` | ★★ | 문서 출처 인용 |
| `mime_type` | ★ | 파일 유형 필터링 |

## 3. 데이터 품질 평가

### 3.1 완성도 분석

| 항목 | 상태 | 비고 |
|------|------|------|
| **모든 item에 name 존재** | ✅ 100% | 양호 |
| **모든 item에 summary 존재** | ✅ 100% | 양호 - 모두 의미있는 한국어 설명 |
| **laws 아이템 highlights** | ⚠️ 67% (14/21) | 7개 아이템에 하이라이트 누락 |
| **kits 아이템 relatedLaws** | ✅ 100% | 모든 kit에 최소 1개 관련법 |
| **kits 아이템 tag** | ✅ 100% | 모든 kit에 태그 존재 |
| **dday 필드** | ⚠️ 12% (3/25) | grant 카테고리에만 존재 (정상) |

### 3.2 언어 일관성

- **전체 한국어**: 모든 필드가 한국어로 작성됨 ✅
- **법령명 표기**: 일관된 형식 ("법률명 제N조 (소제목)") ✅
- **요약 문체**: 경어체/설명체 혼용 없이 일관된 설명체 ✅

### 3.3 데이터 한계점

1. **하이라이트 누락 (laws 도메인)**: 21개 중 7개 아이템에 highlights가 없음
   - 누락 아이템: 주차장법, 학교보건법, 위생교육 안내, 다중이용업소법, 안전시설 완비증명서, 원산지 표시, 가격표시제
   - 이 아이템들은 name + summary만으로 Q&A 생성 가능하나 깊이가 떨어짐

2. **laws 도메인에 relatedLaws 없음**: laws와 kits 간 cross-reference가 별도 매핑 필요

3. **실제 PDF 내용 미반영**: seed 데이터는 메타데이터만 포함, PDF 본문 텍스트는 별도 추출 필요

### 4.2 현재 데이터셋의 gap

- **ActionKit seed 데이터에서 직접 파생된 질문이 거의 없음**: 현재 골든셋은 일반적인 창업 법률 질문 위주
- **세무(tax)/인사(hr)/공고문(grant) 도메인 질문 부재**: legal 카테고리에 편중
- **하이라이트 기반 체크리스트 질문 부재**: seed 데이터의 핵심 강점인 highlights 활용 안됨
- **관련법 참조 질문 부재**: relatedLaws 데이터를 활용한 법적 근거 질문 없음

## 5. Q&A 자동 생성 전략

### 전략 1: 템플릿 기반 직접 생성 (Template-Driven)

seed 데이터의 구조화된 필드를 템플릿에 매핑하여 Q&A를 기계적으로 생성합니다.

**생성 규칙:**

| 템플릿 유형 | 소스 필드 | 질문 패턴 | 답변 소스 | 예상 수량 |
|------------|----------|----------|----------|----------|
| **사실 질문** | item.name + summary | "{name}이란 무엇인가요?" | summary | 46 |
| **체크리스트** | item.highlights[] | "{name} 확인 시 주의사항은?" | highlights 결합 | 14 |
| **법적 근거** | relatedLaw.name + summary | "{kit_name}의 법적 근거는?" | relatedLaws 결합 | 25 |
| **절차 질문** | item.tag + summary | "{tag} 관련 어떤 서류가 필요?" | summary + name | 25 |
| **카테고리 개요** | category.title + items | "{title} 단계에서 확인할 사항은?" | 소속 items 요약 | 10 |

**예시 Q&A (template-driven):**

```json
{
  "question": "건축법 제2조에서 음식점은 어떤 용도로 분류되나요?",
  "ground_truth": "건축물의 용도를 29개 군으로 분류하며, 음식점은 제2종 근린생활시설로 분류됨을 명시합니다.",
  "source_field": "laws.1.items[0].summary",
  "category": "factual"
}
```

```json
{
  "question": "영업신고 시 필요한 건강진단서는 얼마나 걸리나요?",
  "ground_truth": "건강진단수첩(보건증)은 검사 후 수령까지 3~5일 소요됩니다.",
  "source_field": "laws.2.items[1].highlights[0]",
  "category": "procedural"
}
```

**장점:**
- 구현이 단순하고 빠름 (Python 스크립트 100줄 이내)
- seed 데이터가 변경되면 자동으로 Q&A도 갱신
- 100% 정확한 ground_truth (원본 데이터 그대로 사용)

**단점:**
- 질문이 기계적/단조로울 수 있음
- 자연어 다양성 부족

**예상 생성량: ~120개 Q&A**

### 전략 2: LLM 기반 증강 생성 (LLM-Augmented)

seed 데이터를 LLM에 컨텍스트로 제공하여 자연스러운 Q&A를 생성합니다.

**파이프라인:**

```
seed 데이터 → 컨텍스트 구성 → LLM 프롬프트 → Q&A 생성 → 검증 필터링
```

**프롬프트 전략:**

1. **아이템 단위 생성**: 각 item의 name + summary + highlights를 LLM에 제공, 3~5개 질문 생성
2. **카테고리 단위 생성**: 카테고리 전체를 컨텍스트로, 비교/종합 질문 생성
3. **크로스 도메인 생성**: laws + kits를 결합하여 실무 시나리오 질문 생성
4. **난이도 지정**: easy/medium/hard 비율을 프롬프트에서 제어

**예시 프롬프트:**

```
다음 법령 정보를 기반으로 음식점 창업자가 할 수 있는 질문 3개를 생성하세요.
난이도는 medium으로, 답변은 제공된 정보에서만 추출하세요.

[법령: 건축법 제2조 (용도 분류)]
[요약: 건축물의 용도를 29개 군으로 분류하며...]
[핵심사항: 일반음식점은 '제2종 근린생활시설'군에 해당...]
```

**검증 단계:**
- 생성된 ground_truth가 seed 데이터에서 추출 가능한지 확인
- 중복 질문 필터링 (cosine similarity > 0.85 제거)
- 답변 가능성 검증 (RAG로 실제 검색 후 정답률 확인)

**장점:**
- 자연스럽고 다양한 질문 생성
- 실제 사용자 질문 패턴에 가까움
- 난이도/유형 다양화 가능

**단점:**
- LLM 호출 비용 발생
- ground_truth 정확성 검증 필요 (hallucination 위험)
- 재현성 관리 필요 (seed 값 고정 등)

**예상 생성량: ~200~300개 Q&A** (필터링 후 ~150개)

### 전략 3 (보너스): 하이브리드 접근

1단계에서 전략1로 기본 Q&A 120개를 기계적 생성하고, 2단계에서 전략2로 이를 기반으로 paraphrase/증강하여 최종 150~200개를 확보합니다.

## 7. 핵심 발견 및 권장사항

### 7.1 핵심 발견

1. **seed 데이터만으로 최소 120개, 최대 200개+ Q&A 생성 가능** - PDF 파싱 없이도 상당량 확보 가능
2. **highlights 필드가 가장 높은 Q&A 생성 가치** - 구체적이고 실무적인 체크포인트 42개 보유
3. **relatedLaws 필드로 법적 근거 질문 자동 생성 가능** - 38개 법 조항 참조
4. **현재 골든셋(21개)은 seed 데이터 커버리지가 매우 낮음** - 세무/인사/공고문 도메인 완전 부재

### 7.2 즉시 실행 권장사항

1. **전략1 (템플릿) 먼저 구현** → 검증된 기본 Q&A 셋 확보 (1~2시간 소요)
2. **전략2 (LLM)로 증강** → 자연스러운 질문 다양화 (비용 대비 효과 검토 후)
3. **golden_dataset.json 구조 확장**: `source_field` 필드 추가하여 seed 데이터 추적성 확보
4. **도메인 균형 맞추기**: 현재 legal 편중 → tax/hr/grant 도메인 Q&A 추가 필수

### 7.3 제약 사항

- **PDF 본문 텍스트 미포함**: seed 데이터의 summary/highlights만으로는 심화 질문 한계
- **실제 업로드 파일 부재**: `uploads/actionkits/files/` 디렉토리에 파일 없음 → 파일 기반 RAG 테스트 불가
- **laws-kits 간 명시적 매핑 없음**: 동일 PDF를 참조하는 law item과 kit item 간 연결이 path로만 추론 가능
